앞서 정의한 Development Thread 전체 집합을 다시 검토하십시오.
이번 단계의 목적은 새로운 Thread를 최대한 많이 발견하는 것이 아닙니다.
목표는 기존 Thread 집합을 실제 학습 문서로 작성한다고 가정했을 때,
과분할, 과중복, 관점 중복을 제거하면서도
서로 독립적인 개발 지식과 재사용 가능한 문제 해결 판단을 보존하는
최종 Development Thread 집합을 확정하는 것입니다.
반드시 Git 저장소의 전체 commit history와 실제 소스 코드를 다시 확인하여 판단하십시오.
기존 Thread 정의와 제목만 보고 평가하지 마십시오.
1. 핵심 판단 원칙
   Thread 간 중복 여부는 commit 중복으로 판단하지 마십시오.
   두 Thread가 같은 commit을 일부 공유하더라도,
   각각 다른 개발 문제와 다른 설계 판단을 설명한다면
   둘 다 유지할 수 있습니다.
   반대로 서로 다른 commit을 사용하더라도
   실제 학습 문서에서 설명하게 될 핵심 코드, 판단, 실패 조건, 해결 과정이 사실상 같다면
   중복 Thread로 간주할 수 있습니다.
   핵심 질문은 다음과 같습니다.
   "이 두 Thread를 각각 독립된 학습 문서로 작성했을 때,
   독자가 서로 다른 개발 지식과 문제 해결 방식을 배우게 되는가?"
2. 각 Thread를 검토할 때 확인할 질문
   각 Thread와 서로 인접하거나 관련된 Thread를 비교하면서 다음을 확인하십시오.
* 서로 다른 개발 문제를 설명하는가?
* 각각에서 배워야 하는 설계 판단이 다른가?
* 동일한 구현을 단순히 다른 추상화 수준의 제목으로 반복하고 있지는 않은가?
* 한 Thread를 학습하면 다른 Thread의 핵심 내용까지 사실상 모두 이해하게 되는가?
* 작은 Thread가 독립적인 문제 해결 단위로서 재사용 가능한 학습 가치를 가지는가?
* 상위 Thread가 하위 Thread의 세부 구현을 다시 설명하는 대신,
  컴포넌트 연결, 데이터 흐름, 상태 전이, 시스템 불변 조건, 계층 간 계약 등
  별도의 개발 지식을 제공하는가?
3. 유지할 수 있는 중복
   같은 commit이나 같은 코드 일부를 공유하더라도
   서로 다른 개발 판단을 설명한다면 별도의 Thread로 유지할 수 있습니다.
   예를 들어 다음 두 Thread는 동시에 존재할 수 있습니다.
   하위 Thread:
* parser 자체의 구현
* grammar 처리
* 입력 boundary
* parser 내부 error handling
  상위 Thread:
* socket 입력
* parser
* dispatcher
* handler
* response 생성
* 각 컴포넌트 사이의 contract
* end-to-end 요청 처리 흐름
  이 경우 일부 parser 관련 commit이 두 Thread에 포함되더라도 문제가 아닙니다.
  하위 Thread는 parser라는 독립 컴포넌트를 어떻게 구현하는지를 설명하고,
  상위 Thread는 parser가 전체 요청 처리 과정에서 어떤 역할과 계약을 가지는지를 설명하기 때문입니다.
  즉, 코드 중복보다 학습 관점의 차이를 우선하십시오.
4. 제거하거나 재정의해야 하는 중복
   다음과 같은 경우에는 Thread 병합, 제거 또는 범위 재정의를 우선하십시오.
   Thread A와 Thread B가 다음 내용을 대부분 공유하는 경우:
* 같은 핵심 구현
* 같은 핵심 코드
* 같은 테스트
* 같은 boundary condition
* 같은 실패 조건
* 같은 설계 판단
* 같은 문제 해결 과정
  그리고 차이가 사실상 제목이나 추상화 수준의 표현뿐이라면
  별도 Thread로 유지하지 마십시오.
  예를 들어 다음과 같은 구조는 재검토해야 합니다.
  Thread A:
* 특정 기능 구현
* 그 기능의 핵심 로직
* 해당 기능의 예외 처리
  Thread B:
* 같은 기능을 더 포괄적인 제목으로 표현
* 실제 commit과 설명 내용도 거의 동일
  이 경우 상위 제목을 하나 더 붙였다는 이유만으로 별도 Thread를 만들지 마십시오.
  Thread 수가 줄어드는 것을 문제로 취급하지 마십시오.
5. 과분할 검토
   작은 Thread가 다음 조건에 해당한다면
   독립 Thread로 유지할 필요가 있는지 반드시 검토하십시오.
* 단순 helper 추가
* 단순 wiring
* 단순 rename 또는 mechanical refactoring
* 독립적인 설계 판단이 거의 없는 소규모 변경
* 다른 Thread의 구현 과정에서 자연스럽게 설명할 수 있는 내용
* 별도 문서로 만들 경우 대부분 다른 Thread의 설명을 반복하게 되는 내용
  이러한 변경은 별도 Thread보다는
  더 큰 문제 해결 과정의 일부로 포함하는 것이 적절할 수 있습니다.
  단, 코드량이나 commit 수가 적다는 이유만으로 제거하지 마십시오.
  다음과 같은 경우에는 작은 Thread도 독립적으로 유지할 수 있습니다.
* 명확한 독립 문제를 해결한다.
* 중요한 boundary condition을 다룬다.
* 독립적인 알고리즘 판단이 있다.
* 실패와 수정 과정 자체가 학습 가치가 있다.
* 이후 유사한 문제에서 그대로 재사용 가능한 판단을 제공한다.
6. 상위 Thread 검토
   상위 수준 Thread는 단순히 여러 하위 Thread의 내용을 요약하기 위한 목적으로 만들지 마십시오.
   상위 Thread가 독립적으로 유지되려면
   하위 구현과 구별되는 별도의 학습 가치가 있어야 합니다.
   예를 들어 다음과 같은 관점입니다.
* 여러 컴포넌트의 연결 방식
* end-to-end 데이터 흐름
* 상태의 생성, 변화, 종료까지의 lifecycle
* 시스템 수준 invariant
* 계층 또는 모듈 간 contract
* 주요 processing pipeline
* 동시성 관계
* 데이터 일관성 유지 방식
* 에러가 계층 사이에서 전달되는 방식
* 아키텍처 변화와 그에 따른 책임 재배치
  상위 Thread가 이러한 별도 지식을 제공하지 않고
  하위 Thread의 내용을 단순히 다시 요약하거나 묶는 역할만 한다면
  제거하거나 다른 범위로 재정의하십시오.
  또한 상위 Thread를 하위 Thread commit의 단순 합집합으로 만들지 마십시오.
  상위 Thread에는 그 상위 관점을 이해하는 데 필요한 대표 commit만 선택하십시오.
7. Thread 간 포함 관계 검토
   Thread는 서로 완전히 배타적일 필요가 없습니다.
   하나의 작은 Thread가 더 큰 개발 과정의 일부가 될 수 있고,
   하나의 commit이 여러 Thread에 포함될 수도 있습니다.
   그러나 다음 관계는 구분하십시오.
   유효한 관계:
* 하위 Thread는 특정 알고리즘 또는 컴포넌트 구현을 설명한다.
* 상위 Thread는 여러 컴포넌트 사이의 연결과 시스템 흐름을 설명한다.
  문제가 되는 관계:
* 하위 Thread와 상위 Thread가 실질적으로 같은 코드와 같은 판단을 같은 방식으로 설명한다.
* 상위 Thread가 하위 Thread의 내용을 제목만 바꾸어 다시 서술한다.
  포함 관계 자체가 문제가 아니라,
  학습 내용의 실질적 중복이 문제입니다.
8. 카테고리화 여부 판단
   최종 Thread 집합을 카테고리로 나누는 것이
   탐색과 학습 순서를 실제로 개선하는지 판단하십시오.
   카테고리는 필요한 경우에만 만드십시오.
   다음 조건을 만족할 때 카테고리를 사용할 수 있습니다.
* 여러 Thread가 명확한 상위 개발 영역을 공유한다.
* 프로젝트 규모가 커서 flat 목록만으로는 전체 구조를 파악하기 어렵다.
* 카테고리가 Thread 간 관계나 학습 순서를 이해하는 데 실질적인 정보를 제공한다.
  다음과 같은 경우에는 카테고리를 만들지 마십시오.
* Thread 수가 적다.
* 자연스러운 상위 그룹이 없다.
* 분류를 위해 억지로 경계를 만들어야 한다.
* 카테고리가 단순한 디렉터리 정리에 불과하다.
* 카테고리가 없어도 Thread 간 관계와 학습 순서를 충분히 이해할 수 있다.
  카테고리 개수와 Thread 개수를 미리 정하지 마십시오.
9. 학습 가치 기준
   Thread의 유지 여부는 코드량이나 commit 수로 판단하지 마십시오.
   다음 질문을 가장 중요한 기준으로 사용하십시오.
   "이후 유사한 개발 문제를 다시 만났을 때,
   이 Thread를 독립적으로 학습한 경험이
   별도의 구현 판단이나 문제 해결 전략을 재현하는 데 도움이 되는가?"
   답이 "그렇다"라면 독립 Thread로 유지할 가치가 있습니다.
   답이 "아니다"이고
   다른 Thread를 학습하는 것만으로 해당 지식이 충분히 습득된다면
   병합하거나 제거하십시오.
10. 허용되는 변경
    필요하다면 제한 없이 다음 작업을 수행할 수 있습니다.
* Thread 병합
* Thread 제거
* Thread 신규 생성
* Thread 범위 축소
* Thread 범위 확대
* commit 추가
* commit 제거
* commit 순서 조정
* 동일 commit을 여러 Thread에 유지
* 상위 Thread 제거
* 상위 Thread 재정의
* 하위 Thread 재정의
* 카테고리 생성
* 카테고리 제거
* Thread 제목 변경
  기존 Thread 개수, 번호, 순서, 카테고리 구조에 얽매이지 마십시오.
  단, 단순히 Thread 수를 줄이는 것을 목표로 해서는 안 됩니다.
  목표는 "최소한의 Thread 수"가 아니라,
  "중복 없이 필요한 개발 관점을 모두 보존하는 최종 Thread 집합"
  입니다.
11. 최종 문서 중복 시뮬레이션
    최종 Thread 집합을 확정하기 전에
    모든 Thread에 대해 다음 상황을 가정하십시오.
    "각 Thread를 하나의 독립된 학습 문서로 작성한다."
    그 상태에서 관련 Thread끼리 비교하여
    두 문서가 다음 내용을 과도하게 반복하게 되는지 확인하십시오.
* 같은 핵심 코드
* 같은 구현 설명
* 같은 테스트
* 같은 boundary condition
* 같은 실패 조건
* 같은 설계 판단
* 같은 문제 해결 과정
  반복이 크고 별도의 학습 가치가 없다면
  Thread를 병합, 제거 또는 재정의하십시오.
  반대로 일부 코드와 commit이 겹치더라도
  서로 다른 문제 해결 지식과 설계 판단을 전달한다면
  두 Thread를 모두 유지하십시오.
12. 최종 완전성 검증
    중복을 제거하는 과정에서
    프로젝트를 이해하는 데 필요한 개발 관점까지 함께 사라지지 않았는지 확인하십시오.
    최종 Thread 집합을 따라가면 다음을 이해할 수 있어야 합니다.
* 주요 기능이 어떻게 구현되었는가
* 중요한 알고리즘과 자료구조가 어떻게 선택되고 수정되었는가
* 주요 boundary와 failure case를 어떻게 처리했는가
* 컴포넌트들이 어떻게 연결되는가
* 데이터와 상태가 시스템 안에서 어떻게 이동하고 변화하는가
* 중요한 설계 판단이 어떤 문제에서 나왔는가
* 실패한 접근과 수정 과정에서 무엇을 배울 수 있는가
* 프로젝트 전체를 구성하는 주요 pipeline 또는 architecture가 무엇인가
  중복 제거 때문에 이러한 핵심 관점이 누락되어서는 안 됩니다.
13. 출력 규칙
    최종적으로 확정된 Development Thread 전체 집합만 출력하십시오.
    분석 과정은 출력하지 마십시오.
    다음 내용도 최종 출력에 포함하지 마십시오.
* 어떤 Thread를 제거했는지에 대한 보고
* 병합 이유
* 중복 평가 결과
* 판단 과정
* 검토 메모
* 대안 Thread 구성
  카테고리가 학습 구조를 실질적으로 개선하는 경우에만 카테고리를 포함하십시오.
  필요하지 않다면 flat Thread 목록으로 출력하십시오.
  각 Thread에는 반드시 다음을 포함하십시오.
* 한국어 제목
* 영어 제목
* commit 목록
  각 Thread의 commit은 해당 개발 과정을 가장 자연스럽게 학습할 수 있는 순서로 배치하십시오.
  동일 commit이 여러 Thread에서 필요하다면 중복 포함할 수 있습니다.
  최종 출력은 재검토가 끝난 "확정된 Thread 집합" 자체만 보여주십시오.
