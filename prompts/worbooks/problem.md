# DevThread 가 존재하는 웹 LLM 프로젝트 폴더용 프롬프트 
현재 GPT 프로젝트에 축적된 프로젝트 메모리와 과거 DevThread 작업 기록을 바탕으로 개발자 기술면접 워크북을 작성해라.
원격 저장소나 추가 자료 제공을 요구하지 마라. 현재 프로젝트에서 실제로 확인 가능한 정보만 사용하고, 확인할 수 없는 파일명·함수명·구현 세부사항은 추측하지 마라.
1. 면접 지점 선별
전체 Thread와 커밋 작업 기록을 검토해 면접관이 실제로 질문하거나 직접 구현을 요구할 가치가 있는 지점을 선별해라.
다음을 중심으로 평가하되 프로젝트 성격에 맞지 않는 기준은 적용하지 마라.
언어와 런타임의 핵심 원리
자료구조와 알고리즘
상태와 invariant
메모리·리소스·lifecycle
I/O·네트워크·동시성·비동기 처리
데이터 정합성과 트랜잭션
오류·실패·복구 처리
성능과 복잡도
보안
API·컴포넌트·시스템 경계
설계 선택과 trade-off
테스트하기 까다로운 경계 조건
프로젝트 밖에서도 일반화할 수 있는 개발 지식
단순 boilerplate, 반복 구현, 설정 변경, 프로젝트에 지나치게 특수한 내용은 낮게 평가해라.
같은 역량을 여러 Thread가 반복하면 가장 대표적인 지점을 선택하고 나머지는 연관 위치로 묶어라.
우선순위는 다음과 같이 분류한다.
S: 반드시 준비. 질문과 직접 구현 모두 가치가 높음
A: 준비 가치가 높음. 질문 또는 핵심 구현 가능성이 높음
B: 구현보다 설계·개념 설명 준비가 중요함
C: 별도 면접 준비 항목으로 만들 필요가 낮음
먼저 다음 표로 전체 선별 결과를 작성해라.
우선순위Thread커밋 메시지관련 위치핵심 면접 주제선별 이유질문형구현형연관 Thread
관련 위치에는 프로젝트 메모리에서 실제로 확인 가능한 경우에만 파일·함수·클래스·컴포넌트 등을 적어라.
2. 면접 워크북 작성

2. 상세 워크북
S/A 면접 포인트는 여러 개의 별도 Markdown 파일로 나누어 작성해라.
가능하면 서로 관련된 면접 주제를 같은 문서로 묶고 파일명에 주제를 반영해라.
예:

02-io-and-error-recovery.md

02-workbook-02.md
03-workbook-03.md

문서 수를 미리 제한하지 마라. 프로젝트 규모와 선별된 면접 포인트 수에 따라 필요한 만큼 파일을 만들어라.
각 면접 포인트의 설명 밀도를 유지하기 위해 문서 수를 줄이는 대신 내용을 축약하거나 항목을 생략하지 마라.
3. 완전성 검증
모든 상세 문서를 작성한 뒤 00-interview-map.md의 S/A 항목과 대조해라.
각 S/A 항목은 반드시 다음 중 하나의 상태여야 한다.
독립적인 상세 워크북 항목으로 작성됨
다른 대표 면접 포인트에 명시적으로 통합됨
어느 쪽에도 속하지 않는 S/A 항목을 남기지 마라.
B/C 항목은 상세 워크북을 만들 필요가 없다.
4. 응답 방식
채팅 답변에 전체 워크북 내용을 다시 복사하지 마라.
생성한 문서 파일들의 목록과 각 파일의 역할만 간단히 알려줘. 
# DevThread 가 존재하지 않는 로컬 에이전트용 프롬프트 
프로젝트 위치: 
`<PROJECT_PATH>` 
위 로컬 프로젝트를 전체적으로 분석하여 개발자 기술면접 대비용 워크북을 작성해라. 
DevThread나 별도의 사전 분석 문서는 없다고 가정한다. 원본 코드, Git 이력, 테스트, 설정 파일, 문서를 직접 조사하여 판단한다. 
## 1. 프로젝트 조사 
먼저 프로젝트 전체 구조와 Git 이력을 조사해라. 
필요에 따라 다음을 직접 확인한다. 
* 디렉터리와 파일 구조
* 주요 언어, 프레임워크, 라이브러리
* 애플리케이션의 주요 실행 흐름
* 핵심 도메인 로직
* 주요 모듈과 경계
* 데이터와 상태의 흐름
* 오류 처리
* 테스트
* 설정 및 인프라
* Git commit history
* 중요한 commit의 diff
* 함수, 클래스, 컴포넌트의 정의와 사용처 
README만으로 판단하지 말고 실제 코드와 변경 이력을 근거로 분석해라. 
저장소 규모가 크더라도 일부 파일만 보고 전체를 판단하지 마라. 먼저 구조를 파악한 뒤 면접 가치가 높은 영역을 체계적으로 조사해라. 
## 2. 면접 지점 선별 
면접관이 이 저장소를 직접 살펴봤다고 가정하고 다음 두 종류의 지점을 찾아라. 
1. 구현과 설계 이유를 질문하기 좋은 지점
2. 면접 중 핵심 부분을 다시 구현해보라고 하기 좋은 지점 
프로젝트 특성에 맞게 다음 요소를 평가한다. 
* 언어와 런타임의 핵심 원리
* 자료구조와 알고리즘
* 상태와 invariant
* 메모리, ownership, resource lifecycle
* I/O, 네트워크, 동시성, 비동기 처리
* 데이터 모델링과 정합성
* 트랜잭션
* 오류, 실패, 복구
* API와 시스템 경계
* 보안
* 성능과 복잡도
* 캐시
* 상태 관리
* 테스트하기 어려운 경계 조건
* 설계 선택과 trade-off
* 프로젝트 밖에서도 일반화할 수 있는 개발 지식 
프로젝트에 존재하지 않는 평가 기준은 억지로 적용하지 마라. 
다음은 낮게 평가한다. 
* boilerplate
* 자동 생성 코드
* 단순 wiring
* 반복 코드
* 설정값 변경만 있는 commit
* 라이브러리 사용법 암기에 가까운 부분
* 프로젝트에 지나치게 특수하여 일반적인 면접 가치가 낮은 부분 
## 3. 우선순위 
각 후보를 다음으로 분류한다. 
* **S**: 반드시 준비. 질문과 직접 구현 모두 가치가 높음
* **A**: 준비 가치가 높음. 질문 또는 핵심 구현 가능성이 높음
* **B**: 직접 구현보다 설계와 개념 설명 준비가 중요함
* **C**: 별도의 면접 준비 항목으로 만들 필요가 낮음 
같은 역량을 여러 파일이나 commit에서 반복해서 확인하는 경우 모든 지점을 별도 문제로 만들지 마라. 
가장 대표적인 구현을 선택하고 나머지는 연관 위치로 묶어라. 
## 4. 마스터 인덱스 작성 
다음 위치에 결과 디렉터리를 생성한다. 
`<PROJECT_PATH>/interview-workbook/` 
먼저 다음 파일을 작성한다. 
`00-interview-map.md` 
다음 표를 포함한다. 
| 우선순위 | 주제 | Commit | 파일/함수/클래스 | 핵심 면접 포인트 | 선별 이유 | 질문형 | 구현형 | 연관 위치 | 상세 문서 |
| ---- | -- | ------ | --------- | --------- | ----- | --- | --- | ----- | ----- | 
Commit이 중요한 근거인 경우 commit hash와 message를 함께 적는다. 
현재 Git 이력에서 의미 있는 commit을 특정할 수 없다면 억지로 commit을 연결하지 마라. 
파일, 함수, 클래스, 컴포넌트 이름은 실제 저장소에 존재하는 것만 사용한다. 
## 5. 상세 면접 워크북 작성 
S와 A로 선정된 항목을 중심으로 상세 워크북을 작성한다. 
결과를 하나의 거대한 Markdown 파일에 넣지 마라. 
서로 관련된 주제끼리 묶어 여러 Markdown 파일로 나눈다. 
예: 
* `01-memory-and-resource.md`
* `02-io-and-error-handling.md`
* `03-state-and-concurrency.md`
* `04-data-and-transactions.md` 
프로젝트 성격에 맞는 파일명을 스스로 결정한다. 
주제별 분류가 부자연스러우면 다음처럼 순차적으로 나눈다. 
* `01-workbook-01.md`
* `02-workbook-02.md`
* `03-workbook-03.md` 
한 상세 문서에는 원칙적으로 최대 5~7개의 면접 포인트만 포함한다. 
문서 개수를 미리 제한하지 마라. 
문서 수를 줄이기 위해 설명을 축약하거나 S/A 항목을 생략하지 마라.

불필요한 교과서식 장문 설명은 피한다. 
## 답변 핵심 키워드 
답변 전체를 암기하지 않고 스스로 재구성할 수 있도록 핵심 키워드 3~7개를 적는다. 
## 꼬리 질문과 핵심 답변 
면접관이 이해도를 더 확인하기 위해 이어서 질문할 만한 내용을 작성한다. 
필요한 만큼 짧은 모범 답변을 함께 작성한다. 
## 백지 구현 
원본 구현 코드를 보여주지 마라. 
실제 프로젝트의 핵심 아이디어를 면접에서 10~30분 안에 다시 작성할 수 있는 크기로 축소하여 문제를 만든다. 
포함할 것: 
* 구현 목표
* 함수, 클래스, 컴포넌트 또는 API 인터페이스
* 입력
* 출력
* 반드시 만족해야 할 조건
* 경계 조건
* 실패 조건
* 필요한 제약사항 
필요하면 빈 skeleton만 제공한다. 
원본 코드의 구조를 사실상 그대로 알려주는 pseudocode는 작성하지 마라. 
전체 feature나 전체 서비스를 다시 만들라고 요구하지 마라. 
프레임워크 boilerplate 작성 문제가 아니라 개발자의 기본기와 판단을 확인할 수 있는 부분을 우선한다. 
## 구현 후 자가 검증 
원본을 다시 보기 전에 직접 확인할 체크리스트를 작성한다. 
해당 문제에 필요한 항목만 사용한다. 
예: 
* 정상 경로
* 경계값
* 실패 경로
* 상태 변화
* invariant
* resource cleanup
* 데이터 정합성
* 중복/누락 처리
* 동시성
* 비동기 순서
* 보안
* 시간/공간 복잡도
* 요구사항 충족 
원본 코드와 줄 단위로 동일한지를 검사하는 항목은 만들지 마라. 
## 구현 후 설명할 것 
직접 구현한 뒤 면접관에게 설명해야 할 핵심 판단과 trade-off를 3~5개 적는다. 
## 원본 확인 위치 
직접 구현을 끝낸 뒤 원래 프로젝트로 돌아가 비교할 수 있도록 실제 위치를 정확히 적는다. 
가능한 경우 다음을 포함한다. 
* 파일 경로
* 함수
* 클래스
* 컴포넌트
* commit hash
* commit message
* 관련 테스트
* 연관 구현 위치 
원본 코드를 이 섹션에 복사하지 마라.

## 7. Git 이력 활용 원칙 
현재 구현만 보지 말고 필요한 경우 Git history를 이용하여 설계가 어떻게 형성되었는지 확인한다. 
특히 다음 경우 commit diff를 조사한다. 
* 현재 코드만으로 설계 의도가 불명확한 경우
* 오류 처리나 lifecycle이 여러 commit에 걸쳐 발전한 경우
* 알고리즘이나 자료구조가 교체된 경우
* 버그 수정이 중요한 면접 포인트를 드러내는 경우
* 테스트 추가가 숨은 경계 조건을 보여주는 경우 
모든 commit을 워크북 항목으로 만들 필요는 없다. 
Git 이력은 현재 코드의 의미와 개발자의 판단을 이해하기 위한 근거로 사용한다. 
## 8. 소스 코드 보호 
면접 워크북 생성 과정에서 원본 프로젝트 코드는 수정하지 마라. 
다음 디렉터리 아래의 Markdown 문서만 새로 생성하거나 수정한다. 
`<PROJECT_PATH>/interview-workbook/` 
빌드나 테스트를 실행해야 분석에 도움이 되는 경우 실행할 수 있지만, 프로젝트 파일을 자동 수정하는 명령은 사용하지 마라. 
생성 파일, formatting 변경, dependency update, lockfile 변경을 남기지 마라. 
## 9. 완전성 검증 
상세 문서 작성이 끝나면 `00-interview-map.md`와 모든 상세 문서를 다시 대조한다. 
모든 S/A 항목이 반드시 다음 중 하나에 해당해야 한다. 
* 독립적인 상세 워크북 항목으로 작성됨
* 다른 대표 항목에 통합되었으며 그 관계가 명시됨 
어느 쪽에도 속하지 않는 S/A 항목을 남기지 마라. 
반대로 하나의 역량을 확인하는 거의 동일한 문제를 여러 번 만들지 마라. 
상세 문서의 각 원본 위치가 실제 프로젝트에 존재하는지도 확인한다. 
## 10. 최종 산출물 
최종 결과는 다음 형태의 파일 세트여야 한다. 
```text
<PROJECT_PATH>/interview-workbook/
├── 00-interview-map.md
├── 01-....md
├── 02-....md
├── 03-....md
└── ...
``` 
파일 수는 프로젝트 규모와 면접 포인트 수에 따라 결정한다. 
채점표, 점수, PASS/FAIL 판정은 만들지 마라. 
백지 구현에는 정답 코드를 포함하지 마라. 
작업 완료 후 채팅에는 생성한 파일 목록과 각 파일의 역할만 간단히 보고해라.
