다음 두 로컬 디렉터리를 사용해 기존 면접 워크북의 **빈 답안만 채워라.**

* 워크북 디렉터리: `<WORKBOOK_DIR>`
* 원본 프로젝트 디렉터리: `<PROJECT_DIR>`

작업 범위는 아래 3가지뿐이다.

1. `꼬리 질문`

   * 질문만 있고 답변이 없는 경우, 각 질문 바로 아래에 짧은 모범답변을 작성한다.
   * 원본 프로젝트에서 확인 가능한 구현과 설계 사실을 근거로 답한다.
   * 프로젝트 특수사항과 일반적인 개발 원칙을 구분한다.

2. `백지 구현`

   * `// 직접 구현`으로 비어 있는 코드 블록을 모범 구현으로 채운다.
   * 먼저 `<PROJECT_DIR>`에서 해당 문제와 대응되는 실제 구현을 확인한다.
   * 워크북 문제와 원본 구현의 범위가 같거나 거의 같으면, 원본의 핵심 로직을 그대로 반영하고 학습에 필요한 설명 주석을 추가한다.
   * 워크북 문제가 원본보다 축소·추상화되어 있다면, 원본의 알고리즘, 상태 전이, invariant, 오류 처리, 리소스 lifecycle, 핵심 설계 판단을 유지한 채 문제 크기에 맞게 축소하여 작성한다.
   * AI가 임의의 다른 알고리즘이나 별도 해법으로 대체하지 않는다.
   * 프로젝트 의존적인 주변 코드나 불필요한 boilerplate는 워크북 문제에 필요하지 않으면 제외한다.
   * 설명 주석은 모든 줄에 달지 말고, invariant, 경계 조건, 실패 처리, ownership 변화, 자명하지 않은 계산처럼 면접 학습에 중요한 부분에만 추가한다.

3. `구현 후 설명할 것`

   * 질문이나 설명 항목만 있고 답이 없는 경우, 각 항목 바로 아래에 면접에서 말할 수 있는 모범답변을 작성한다.
   * 현재 원본 구현이 왜 그렇게 작성되었는지 설명하되, 코드에서 확인할 수 없는 의도는 추측하지 않는다.
   * 다른 합리적인 해법이 있다면 필요한 경우에만 짧게 trade-off로 언급한다.

그 외 기존 내용은 수정하지 않는다.

특히 다음은 새로 작성하거나 확장하지 않는다.

* 기존 `면접 질문`
* 기존 `30초 모범 답변`
* 기존 `답변 핵심 키워드`
* `백지 구현`의 문제 설명, 인터페이스, 조건, 제약
* `구현 후 자가 검증`
* `원본 확인 위치`
* 새로운 면접 질문
* 1~2분 확장 답변
* 새로운 학습 문서
* 별도의 비교 문서나 정리 문서

원본 프로젝트 사용 원칙:

* `<PROJECT_DIR>`는 단순 참고가 아니라 모범답안의 기준 구현으로 사용한다.
* 프로젝트에서 실제로 확인할 수 없는 파일명, 함수명, 타입, 구현 세부사항, 설계 의도는 만들지 않는다.
* 원본 구현과 워크북 skeleton의 형태가 다르면, 형태는 워크북에 맞추되 핵심 동작과 설계 판단은 원본을 따른다.
* 원본과 다른 해법을 주 모범답안으로 선택하지 않는다.

파일 처리:

* 기존 Markdown 구조, 항목 순서, 파일 분할을 유지한다.
* 기존 워크북 파일을 직접 수정한다.
* 불필요한 새 파일은 생성하지 않는다.
* `00-interview-map.md`는 인덱스이므로 빈 답안 작성 대상이 아닌 한 수정하지 않는다.

작업 완료 후 모든 상세 워크북을 확인하여 다음이 남아 있지 않은지만 검증한다.

* 답변 없는 `꼬리 질문`
* `// 직접 구현`
* 답변 없는 `구현 후 설명할 것`

최종 응답에는 수정한 파일 목록과 남은 빈 답안 존재 여부만 간단히 보고하고, 워크북 전체 내용을 다시 출력하지 않는다.

작업을 시작전 모호한 부분은 먼저 질문한다.
질문이없을 경우 "질문 없음, 준비 완료" 라고 답한다.
